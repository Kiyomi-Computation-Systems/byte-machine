* Byte Machine

State machine generator in the manner of [[https://github.com/nodejs/llparse][llparse]].

Byte Machine is a byte-oriented deterministic state-machine generator for Chez
Scheme. Machines are built with ordinary Scheme procedures into an immutable,
inspectable source IR; a mandatory verifier gates every path to output; and an
offline generator emits deterministic R6RS Scheme. Generated parsers depend only
on a small runtime library — never on the builder, verifier, compiler, or
reference interpreter.

It is a library and source generator, not itself an HTTP parser. A separate
project will use it to define and generate one.

Machines combine byte dispatch, byte classes and sequences, unsigned-integer
fields with checked accumulation, zero-width actions and branches, callbacks,
spans, and counted consumption. The [[file:.reference/source-ir-and-builder.md][source IR and builder reference]] documents
every constructor and node kind.

*Status:* =0.6.1=. v0.6.1 fixes a keyword table's allocation: the runtime walk
every keyword-table state calls copied the prefix it had matched on every byte,
so a header name matching k bytes of a keyword allocated about k²/2 pairs —
downstream, 138 times a request's own size for a run of near-miss
=Transfer-Encoding= fields. The walk now makes one pass over the table and
allocates only its answer, 64 bytes, however much it matched
([[file:.decisions/0054-a-keyword-walk-reads-its-prefix-in-place.md][decision 0054]]).
No regeneration is needed: the ABI, the emitted text and the API are
unchanged. v0.6 makes the emitted parser stop scanning. Chez compiles a
large =case= over integer keys as a **linear scan** — about 0.31 ns per arm
skipped — and the emitter had four of them nested: the state dispatch, the byte
dispatch inside each state, a callback answering =goto=, and the feed entry.
Every one is now a jump, a range test or a binary search, and the callback seam
stopped consing an outcome list nobody read (128 bytes per HTTP header). On
=tarm64osx=, =many-small-headers= runs 90 → 51 ms and a byte-at-a-time parse 39
→ 32; downstream, a 308-byte HTTP request parses **twelve times faster** than
before this release with its llhttp differential unchanged. **The
generated-runtime ABI breaks, 8 → 9** (decision 0052): regenerate, or the
runtime refuses the parser at construction. No graph or parser API changes.
[[file:.plans/milestone-14-close.md][Milestone 14's close]] records the five
decisions, and that one of them ships without meeting this project's own
admission rule — recorded as an exception rather than resolved by widening the
rule. v0.5 lets a parser **start in a mode**: a =uint= field may be
declared =settable= (=make-uint-field='s optional trailing flag, read by
=uint-field-settable?=), and =make-parser= takes an OPTIONAL trailing
=field-initials= alist overriding the declared initials of settable fields — so
two parsers built from one machine can start in two states (a request/response
selector, a lenient-flags bitset) with no entry nodes writing the mode. The
override is range-checked and refused for an unknown, non-settable, duplicate or
out-of-range field; it applies at construction (never mid-parse), and
=parser-reset!= restores it so the mode survives a reset. Both additions are
optional, so no existing machine changes; the generated-runtime ABI bumps 7 → 8
for the settable table it carries (decision 0047). v0.4 added a **pause reason**:
a =pause= node (and a =callback= node returning =callback-pause=) may name an
OPTIONAL reason — a declared =error-declaration= — so a paused parser reports its
own =(code, reason)= through a new =parser-result-pause= accessor, while
=parser-result-error= stays =#f= (a pause is not an error, and it remains
resumable); it bumped the ABI 6 → 7 (decision 0046). v0.3 made the first public-API addition since v0.1: a
=keyword-table= node kind (=make-keyword-table-node= / =make-keyword-entry=,
through =(byte-machine graph)=) that matches a set of keywords tolerating proper
prefixes (=GET= ⊂ =GET-PARAMETER=) with optional per-table ASCII case-folding, and
lowers to one compact table walked by a new runtime op — replacing hundreds of
generated dispatch states (the 47 HTTP methods go from a 242-node trie to one
state); it bumped the ABI 5 → 6 (decisions 0043–0045). v0.2 added
empty-span observability (decision 0042). =src/byte-machine/= holds the
construction API, the verifier, the normalizer and emitter, the reference
interpreter, and the runtime.

** Quick start

Build a *parser* — not the repository. A machine is constructed through the
public =(byte-machine graph)= API, verified, compiled, and emitted as a
self-contained Scheme library that depends only on =(byte-machine runtime)=:

#+begin_src scheme
(import (byte-machine graph) (byte-machine verify) (byte-machine compile))

;; a parser that accepts exactly the byte 'A' (0x41), then stops
(define m
  (make-machine 'simple 'start '() '() '()
    (list (make-error-declaration 'eof 'unexpected-eof "unexpected end of input" #f)
          (make-error-declaration 'rejected 'unexpected-byte "expected 0x41" #f))
    (list (make-byte-dispatch-node 'start
            (list (make-byte-case (make-exact-byte-matcher #x41)
                                  (make-edge 'accept 'advance) #f))
            (make-edge 'reject 'reexecute) 'eof-stop #f)
          (make-stop-node 'accept #f)
          (make-error-node 'reject 'rejected #f)
          (make-error-node 'eof-stop 'eof #f))
    'eof #f))

(compilation-ok? (compile-machine m '()))   ; => #t
#+end_src

The runnable, end-to-end version — construct, compile, emit, load, feed bytes —
is [[file:examples/generate-simple-machine/][=examples/generate-simple-machine/=]]:

#+begin_src bash
chez --libdirs src --program examples/generate-simple-machine/generate.sps
#+end_src

From there, the [[file:.reference/source-ir-and-builder.md][source IR and builder reference]] documents every constructor, and
the [[file:.reference/generated-code-integration-chez.md][generated-code integration guide]] shows how a consumer imports and runs a
generated parser. See [[*Documentation][Documentation]] below for the full set.

** Requirements

- CMake 3.26 or newer
- Chez Scheme 10.4.1 or newer, full system rather than Petite

The Chez version is a floor recording what has actually been verified. v0.1 is
verified on macOS arm64; Linux/Windows amd64 and Linux arm64 are supported but
not yet CI-verified — see the [[file:.reference/portability-matrix.md][portability matrix]].

** R6RS portability

Everything under =src/byte-machine/= imports only =(rnrs)=, and a generated
parser imports only =(rnrs)= and =(byte-machine runtime)=. Porting to another
R6RS system is therefore a question of that system's library search, not of
changing Scheme code. What is Chez-specific is the build and test layer — CMake's
runtime discovery, =--libdirs=/=--program=, the ahead-of-time =compile-program=
lane, and the harness reading =(machine-type)= — so =make test= is Chez-only.

Checked locally, not CI-gated: on *Guile 3.0.11* the whole toolchain runs
unchanged; on *Racket 9.3* it runs once each =.sls= begins with a =#!r6rs= line,
which Chez and Guile accept too. In both, the emitter produced a library
byte-identical to the Chez one, and the generated parser returned the same
statuses and offsets.

#+begin_src bash
guile --r6rs -L src your-program.scm
plt-r6rs ++path src your-program.sps
#+end_src

Generation and execution split cleanly, so a port can be partial: generate on
Chez and deploy only the emitted =.sls= and =(byte-machine runtime)=. The one
=(chezscheme)= import outside =test/= and =bench/= is in
[[file:examples/generate-simple-machine/generate.sps][the example]], which =load=s
the file it just wrote; a consumer importing a generated parser through the
ordinary library path needs nothing like it.

** Building and testing

#+begin_src bash
make build
#+end_src

#+begin_src bash
make test
#+end_src

Other targets: =make doctor= reports the discovered toolchain and stops,
=make dev= builds and runs the harness selection (the build-layer
specifications, the Chez self-test lanes, and the Scheme mutation
suite), =make test-all= runs the complete selection, =make prod= builds the
release configuration, and =make clean= removes the build trees. =make help=
lists them.

The presets work identically without =make=, which matters on Windows:

#+begin_src bash
cmake --preset dev
#+end_src

If discovery cannot find a runtime, point it at one explicitly:

#+begin_src bash
cmake --preset dev -DBYTE_MACHINE_CHEZ_EXECUTABLE=/absolute/path/to/scheme
#+end_src

Both =make dev= and =make test= launch real Chez processes; neither is a
CMake-only target. To work on the build layer alone, with no Scheme runtime
installed, use the =no-scheme= preset instead, which configures and runs only
the build-layer specifications:

#+begin_src bash
cmake --preset no-scheme && ctest --preset no-scheme
#+end_src
